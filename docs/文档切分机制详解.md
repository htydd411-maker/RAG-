## 0. 先用一条流水线看懂全局

很多人卡在"看一点不会一点",是因为一上来就读 `split_text` 的双层 while。先把数据流的形状记住,后面每一步都只是在解释"这一步为什么需要":

| 阶段 | 代码位置 | 做的事 | 本例实测 |
|---|---|---|---|
| ① 版式取块 | `pdfSplitTest_Ch.py:30-36` | pdfminer 按 PDF 排版把文字切成块 | 6 页 → **81 个文本块** |
| ② 摊平成行 | `:36,43` | 每块后面补 `\n`,再按 `\n` 切成行 | **4867 字符 → 248 行**(其中 82 行长度<3,基本是空行) |
| ③ 行合成段 | `:51-58` | 用 buffer 把连续的非空行粘在一起 | min_line_length=1 → **81 段** |
| ④ 段切成句 | `:17-20,70` | 中文按句末标点断句 | **148 句**,平均 31.6 字 |
| ⑤ 句合成块 | `:73-89` | 按 800 字上限攒块,每块前面挂 ≤200 字上文 | **8 个 chunk** |
| ⑥ 灌库 | `vectorSaveTest.py:110-116` | 8 个 chunk → 8 条 1536 维向量 | chroma 里 8 条,ID 由内容哈希决定 |

一句话总概括:**"按版式取块 → 打散成句 → 重新攒成 800 字的、带 200 字上文的块"**。

注意第 ③ 步和第 ⑤ 步的关系:先"合"再"拆"再"合",看起来绕,但三次动作目的不同 —— ③ 是把被 PDF 换行切断的句子粘回去,⑤ 是把太长的内容重新切到模型能消化的粒度。

调用链是这样的:

```
vectorSaveTest.py:140  vectorStoreSave()
  └── pdfSplitTest_Ch.getParagraphs(filename, page_numbers, min_line_length)   # :94
        ├── extract_text_from_pdf()   # :24   做 ①②③  → 返回"段落"列表
        └── split_text(paragraphs, 800, 200)   # :68  做 ④⑤  → 返回 chunk 列表
  └── MyVectorDBConnector.add_documents(chunks)          # :110  做 ⑥
        └── generate_vectors(data, max_batch_size=25)    # :83
```

`getParagraphs` 这个名字有误导性 —— 它返回的**不是段落,是 chunk**。段落只是中间产物。

## 1. 第一刀:pdfminer 按"版式"取文本块

```python
for i, page_layout in enumerate(extract_pages(filename)):      # :30
    if page_numbers is not None and i not in page_numbers:      # :32
        continue
    for element in page_layout:
        if isinstance(element, LTTextContainer):                # :34
            full_text += element.get_text() + '\n'              # :35
```

**为什么不用 `pdfminer.high_level.extract_text()` 一句话把全文拿出来?**
因为这里要的是**版式信息**。`extract_pages` 返回的每一页是一个布局对象,里面按元素类型分:`LTTextContainer`(文字容器,段落/表格单元/标题都是它)、`LTImage`(图)、`LTFigure`、`LTRect`(线条)。代码只保留 `LTTextContainer`,所以图片、装饰线、页眉背景框全被丢掉了 —— 这是**免费获得的降噪**,不需要额外写过滤逻辑。

`element.get_text()` 返回的是**这一块在 PDF 里的原始多行文本**,内部已经带 `\n`(PDF 排版时每行是一个 text line)。这正是为什么后面还需要第 ③ 步:一行并不代表一句话。

`page_numbers` 是页级过滤,`i` 从 0 开始。`PAGE_NUMBERS=None` 表示全要(`vectorSaveTest.py:43`);`tools/pdfSplitTest_En.py:106` 里演示了 `[2, 3]` 只取第 3、4 页。

> 实测:健康档案 6 页,共 81 个 `LTTextContainer`,`full_text` 4867 字符。

## 2. 第二刀:把被排版切断的行粘回"段"

```python
lines = full_text.split('\n')                                  # :43
for text in lines:
    if len(text) >= min_line_length:                            # :52
        buffer += (' '+text) if not text.endswith('-') else text.strip('-')   # :53
    elif buffer:                                                # :54
        paragraphs.append(buffer)                               # :55
        buffer = ''                                             # :56
if buffer:                                                      # :57
    paragraphs.append(buffer)
```

逻辑其实就两句:**"够长的行就往 buffer 上粘;遇到太短的行(含空行)就把 buffer 当成一段交货。"**

三个容易看懂又容易看错的点:

1. **`min_line_length` 的真正含义是"什么算分隔符"。** 一行长度低于它,就被当作段落边界信号,而不是正文。
2. **`' ' + text`**:粘回时补一个空格,因为 PDF 里换行的位置是没有空格的(英文尤其如此)。
3. **`text.endswith('-')` → `strip('-')`**:这是英文排版里的**连字符断词**——`process-\ning` 实际是一个词 `processing`,所以去掉 `-` 且**不补空格**。中文里没有这个现象,这段代码对中文是无害的空转。

实测 `min_line_length` 的影响(同一份 PDF):

| min_line_length | 段数 | 平均段长 | 说明 |
|---|---|---|---|
| 1 / 2 / 3 | 81 | 59.1 | 与 2、3 完全相同:因为分隔用的空行长度是 **0**,不是 1 或 2 |
| 5 | 75 | 63.1 | 开始吃掉极短行 |
| **10** | **50** | 89.4 | 标题行("一、基本信息"7 字)被当成噪声滤掉 |
| 30 | 47 | 83.5 | 差别不大 |
| 60 | **1** | 72.0 | 门槛过大:全文只有一行够长,其余全被判为"边界" |

最后一行值得盯一下:`min_line_length=60` 时整份 PDF 只剩 **1 段**。原因是 60 太长,几乎所有行都 `< min_line_length`,于是永远走 `elif buffer` 分支,buffer 一有东西就被立刻清掉。这说明这个参数不是"越大越干净",存在一个甜点区(这份 PDF 大约 5-15)。

而项目用的是 `min_line_length=1`(`vectorSaveTest.py:143`),所以标题**全被保留**:

```
[0] len=5   '健康档案'
[1] len=7   '一、基本信息'
[2] len=163 '张三九,男,出生于 1985 年 5 月 20 日...'
```

保留标题其实是**有利的**(见 §5),但副作用是"健康档案"这四个字在 81 段里出现了 3 次(每人一页的页首),后面会变成 chunk 里的重复内容。

## 3. 第三刀:段 → 句(中英文唯一真正分叉的地方)

中文版**不用 nltk,用一行正则**:

```python
def sent_tokenize(input_string):                                # :17
    sentences = re.split(r'(?<=[。！？；?!])', input_string)      # :18
    return [s for sentence in sentences if s.strip()]           # :19(意译)
```

`(?<=[。！？；?!])` 是**回顾式零宽断言**:"在句末标点之后切一刀,但标点本身留在前半句"。所以不会像 `split('。')` 那样把句号弄丢。注意它**只认句末标点,不认逗号**——这是本项目切分粒度的关键设定:

- 好处:不会因为一串逗号把一句话切得稀碎,语义单元完整;
- 代价:句子可以很长。实测最长的一段 260 字,里面若只有一个句号就是一句。

英文版([`pdfSplitTest_En.py:19-23`](../RagLangChainTest-main/tools/pdfSplitTest_En.py))换成 `nltk.tokenize.sent_tokenize`,并且尝试从仓库自带的 `other/punkt_tab` 加载离线数据。**这条路目前是坏的**,详见 §6。

实测:81 段 → **148 句**,平均 31.6 字。前 3 句:

```
"健康档案"
"一、基本信息"
"张三九,男,出生于 1985 年 5 月 20 日,目前 39 岁,已婚,职业为 IT 工程师。"
```

看到了吗 —— **标题也变成了"句子"**。因为它们本来就是独立的段,断句后独立成句,随后被混进正文块里。

## 4. 第四刀:`split_text` 攒出带重叠的块

这是最"折磨"的一段,先看骨架就懂了:

```python
sentences = [s.strip() for p in paragraphs for s in sent_tokenize(p)]   # :70 ★
i = 0
while i < len(sentences):
    chunk = sentences[i]                    # 从第 i 句开始
    overlap = ''                            # ── 往前捞上文
    prev = i - 1
    while prev >= 0 and len(sentences[prev]) + len(overlap) <= overlap_size:
        overlap = sentences[prev] + ' ' + overlap
        prev -= 1
    chunk = overlap + chunk                 # :82 把上文接在最前面
    next = i + 1                            # ── 往后吃正文
    while next < len(sentences) and len(sentences[next]) + len(chunk) <= chunk_size:
        chunk = chunk + ' ' + sentences[next]
        next += 1
    chunks.append(chunk)
    i = next                                # :89 下一块从"没吃完的地方"继续
```

**★ 第 70 行是整套切分的灵魂,也是最大隐患。** 它用列表推导把所有段落的句子**压平成一个全局句子列表**,段落边界到此**彻底消失**。后面攒块时根本不知道也不关心"这句属于哪一段、哪一节、哪个人"。

三个设计意图:

- **为什么要 overlap(重叠)?** 向量检索是"一块一个向量"。如果一块以"他每周饮酒 2-3 次"开头,而上文"这里说的是张三九"在**前一块**里,那这块的向量就丢了主语。重叠 200 字把上文粘进来,让每块自己读得通。
- **为什么按句攒而不按 800 字符硬切?** 硬切(比如 LangChain 的 `CharacterTextSplitter` 用 `chunk_size` 直接切字符)会把一句话劈成两半,两半各自都不可读。按句边界攒,块永远是完整句。
- **为什么 `i = next` 而不是 `i += 1`?** 块与块之间**正文不重叠**,只有 overlap 那段是重复的。实测:8 块合计 6026 字,而全文(81 段)只有 4786 字,多出来的 **1240 字正好就是重叠部分的合计**(0+140+148+158+178+200+189+190=1203,差额是句子拼接时补的空格)。也就是说正文一个字都没被重复入库,重复的只有那 1200 字上文 —— 这就是 `i = next` 的意义。

实测的 8 个块(注意 overlap 是"先加、再往后吃",所以 800 的上限里**已经包含重叠部分**,真正新增内容只有 600-660 字):

| 块 | 总长 | 其中重叠上文 | 开头 | 结尾 |
|---|---|---|---|---|
| chunk[0] | 799 | 0(第一块没有前文) | `健康档案 一、基本信息 张三九,男…` | `…餐后 2 小时血糖为 8.9 毫摩尔/升,也高于正常标准。` |
| chunk[1] | 796 | 140 | `他的腰围为 92 厘米…` | `…并每年进行一次全面体检,以动态评估健康状况。` |
| chunk[2] | 800 | 148 | `2. 增加运动量: 张三九每周应至少…` | `…李四六对阿司匹林过敏,曾出现皮疹和轻度呼吸困难。` |
| chunk[3] | 789 | 158 | `用药。 2018 年: 李四六在怀孕期间…` | `…李四六的健康档案和最近的体检结果,存在以下健康风险:` |
| chunk[4] | 744 | 178 | `肝功能检查显示,谷丙转氨酶(ALT)…` | `…出生于 1978 年 12 月 2 日,目前 45 岁,已婚,职业为银行经理。` |
| chunk[5] | 797 | 200 | `1. 保持正常体重: 李四六目前…` | `…每周不超过两次,每次约 500 毫升啤酒。` |
| chunk[6] | 789 | 189 | `家族病史: 父亲: 高血压和冠心病…` | `…需通过饮食和运动管理体重。 六、医生建议` |
| chunk[7] | 512 | 190 | `腹部超声检查显示肝脏轻度脂肪肝…` | `…定期运动和健康饮食,提升整体生活质量和健康水平。` |

超 800 的块:**0 个**。这份 PDF 没有单句超 800 字的情况,所以那条上限一直没被撑破(但如果遇到,`chunk = overlap + 一个长句` 会直接超过 `chunk_size`,这是个潜在风险,不是当前问题)。

小瑕疵:`:82` 的 `overlap + chunk` **没加分隔符**,而 `:80` 和 `:86` 都加了 `' '`。中文里因为句子本来就以 `。` 结尾,读起来没差别;换成英文就会出现 `...methodThe next` 这种粘字。

## 5. 灌库:8 个 chunk 变成 8 条向量

```python
paragraphs = pdfSplitTest_Ch.getParagraphs(filename=INPUT_PDF,
                                            page_numbers=PAGE_NUMBERS,
                                            min_line_length=1)      # vectorSaveTest.py:140-144
vector_db = MyVectorDBConnector(CHROMADB_COLLECTION_NAME, generate_vectors)
vector_db.add_documents(paragraphs)                                 # :150
```

`add_documents` 里三件事同时发生(`:110-116`):

```python
self.collection.upsert(
    embeddings=self.embedding_fn(documents),          # 8 段文本 → 8 个 1536 维向量
    documents=documents,                              # 原文一起存,检索时好回显
    ids=[hashlib.md5(doc.encode('utf-8')).hexdigest() for doc in documents]  # ★ ID 由内容决定
)
```

`generate_vectors(data, max_batch_size=25)`(`:83`)把文本按 25 条一批送进 embedding 接口。8 条一批就发完了,所以这份 PDF 完全看不出分批逻辑。**换成分卷 PDF 时这个参数才起作用**——注意 `text-embedding-v1/v2` 单批上限是 25,`v3/v4` 是 **10**,如果哪天把 `ONEAPI_EMBEDDING_MODEL` 改成 v3,`max_batch_size=25` 会直接报 400。

**为什么原来每跑一次就多 8 条?(现已修复)**
原版写的是 `ids=[str(uuid.uuid4()) ...]` —— 每次现生成 8 个随机 ID。chromadb **只认 ID、不认内容**,于是同样 8 段文本被当成 8 条全新文档插进去。修复前你库里的现场是:

```
总数 = 32   唯一文本 = 8   重复 = 24   维度 = 1536
每份出现 4 次:  '健康档案 一、基本信息 张三九,男,…'
```

即脚本被跑过 4 次。**这不是切分的问题,是 ID 策略的问题。**

2026-11-03 已改成内容哈希 + `upsert`,并清掉那 32 条老 uuid 记录(老 ID 是新代码永远不会再产生的,不删就永远以副本形式留着)。改后实测连跑三次:

```
第 1 次：条数 = 8   唯一文本 = 8
第 2 次：条数 = 8   唯一文本 = 8
第 3 次：条数 = 8   唯一文本 = 8
ID 形如 38d62411dac85c711ca81c4da5591651（32 位十六进制，无连字符）
```

顺带一条判断技巧:**uuid4 是 36 位带 4 个连字符,md5 hex 是 32 位纯十六进制**,看 ID 长度就能分辨一条记录是哪代代码写的。

注意哈希 ID 只保证"**切分结果一模一样**"时可重复执行。一旦你改了 `min_line_length` / `chunk_size` / PDF 内容,chunk 文本变 → 哈希变 → 新 ID 入库,而**旧 ID 的记录不会自动消失**,新旧混在一起。那时候要做的是显式重建:`cli.delete_collection('demo001')` 再跑一次 `vectorSaveTest.py`。

## 6. 检索端怎么用这 8 块(以及为什么它能答对)

- `main.py:208-210`:`vectorstore.as_retriever(search_type="similarity", search_kwargs={"k": 5})` → 问一次捞 5 块进 prompt
- `mainMemory.py:308-310`:`vectorstore.similarity_search(query=..., k=3)` → 捞 3 块

问"张三九的基本信息是什么"为什么能答全?因为 chunk[0] 里同时含"一、基本信息"这个**标题**和紧跟的正文 —— 这就是 §2 里 `min_line_length=1` 保留标题带来的好处:标题成了检索锚点。

反过来,这也解释了**修复前**为什么检索结果会莫名抖动:库里 32 条里有 24 条是同一块文本的副本,k=5 的名额可能被同一内容的不同副本占掉。现在恒为 8 条之后,k=5 就真的是 5 个不同内容 —— **检索质量的波动少了一个干扰源,剩下的差异才归因于切分本身。**

## 7. 这套切分的真实短板(每条都有上面测出来的证据)

| # | 问题 | 证据 | 最小改法 |
|---|---|---|---|

| 2 | ~~重复灌库:每跑一次多 8 条~~ **已修复(2026-11-03)** | 改前库里 32 = 8×4;改后连跑三次恒为 8 条 | 内容哈希 ID + `upsert`(见 §5);改了切分参数仍需手动 `delete_collection` |
| 3 | `min_line_length=1` 没起到降噪作用,页眉"健康档案"×3 进了正文 | §2 段落明细 [0][19][51] | 设成 10(实测 81 段→50 段,标题被过滤但正文完整),或加一条"整行等于标题就丢弃"的规则 |

## 10. 术语对照

| 代码里的词 | 实际含义 |
|---|---|
| `full_text` | 整个(或指定页)PDF 的纯文本,含换行 |
| `lines` | 排版行,一行不等于一句 |
| `paragraphs` | **版式块**,由连续非空行粘成;不是语义段落 |
| `sentences` | 断句结果,段落边界已丢失 |
| `chunks` | 最终入库单位,= overlap + 若干完整句,≤800 字 |
| `overlap` | 前一块的尾巴,用于保住主语和上下文 |
| `getParagraphs()` | 名字叫"段落",**返回的是 chunks** |
